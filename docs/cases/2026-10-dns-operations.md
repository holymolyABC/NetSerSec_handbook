# 2026-10 DNS 운영 사례 — 식별정보 치환

## 작업 범위

2026-10-12~14의 DNS 운영 대화에서 구성 확인·공개 재귀 의심·로그 분석·시간 보정·신규 A 레코드 추가를 정리했습니다. 이 문서는 원본 로그 전체나 실제 고객 환경의 현재 상태를 보증하지 않습니다. 도메인과 IP는 예제 주소로 치환했습니다.

## 확인된 환경

| 항목 | 근거·수준 |
|---|---|
| named 프로세스 | `-u named -4 -c /etc/named.caching-nameserver.conf -t /var/named/chroot` 출력 확인 |
| 패키지 단서 | DiG `9.3.6-P1-RedHat-9.3.6-25.P1.el5_11.2`. 서버 named 버전과 OS 세부판은 별도 확인 필요 |
| view | `localhost_resolver`, `match-clients any`, `recursion yes` 설정 출력 확인 |
| zone | include된 `named.rfc1912.zones`의 master zone·상대 파일명 확인 |
| 기존 재귀·캐시 설정 | `allow-query any`, `allow-query-cache any` 확인 |
| 로그·디스크 | named.run 6.3GB, `/var` 20% 사용·37GB 여유 |
| 자원 | named RES 약3.7GB·메모리96.6%, 시스템 swap 약3.8GB |

## 사건과 판단

| 관찰 | 확인된 사실 | 판단 한계 |
|---|---|---|
| 외부의 무관한 도메인 질의와 응답 | 요청·응답·외부 DNS 질의가 캡처에 나타남 | 오용 가능성 높음. 공격자·지연 원인을 단독 확정하지 않음 |
| 캐시 denied 다수 | 해당 요청은 거부됨 | 모든 외부 재귀 차단 완료를 증명하지 않음 |
| REFUSED resolving | 다른 DNS가 우리 서버의 질의를 거부 | 그 IP가 최초 요청자라는 뜻 아님 |
| NOTAUTH 영역 전송 | 관리하지 않는 zone 전송 요청 거부 | 이 로그에서 전송 성공·유출 확인 안 됨 |
| 시계가 다음날 새벽 | KST 설정은 정상이지만 실제 시각이 앞섬 | 로그 입력 간격이 있어 정확한 오프셋은 재측정 필요 |
| 뒤에 전날 저녁 로그 등장 | 시간 보정과 일치 | 최종 RTC·지속 동기화 완료 자료는 없음 |

## 신규 A 레코드 — 적용 검증됨

요청 내용을 예제로 재구성하면 다음과 같습니다.

```dns
agri    IN    A    192.0.2.228
```

원본 작업 출력에서 serial `2026101401`, `named-checkzone ... OK`, `rndc reload ... zone reload queued`, 최종 권한 서버 직접 질의의 `NOERROR`·`aa`·A 응답·TTL 86400이 확인됐습니다. 따라서 **해당 권한 서버에 A 레코드가 반영됨**은 확인됐습니다. 실제 이름 철자는 최초 언급 후 요청서 기준으로 정정됐으며, 매뉴얼에는 최종 요청을 기준으로 기록합니다.

**검증되지 않은 것:** 모든 공용 리졸버의 반영, 웹 로그인, 1025 외부 접근, TLS, 포트 생략 프록시 완료.

## 완료로 기록하지 않는 제안

- 재귀·캐시 ACL 최종 전체 설정과 허용/비허용 외부 테스트 결과.
- `security.log`·`transfer.log` 분리 및 순환 저장 적용 결과.
- 등록기관의 미사용 네임서버·glue 정리 완료.
- NTP 구성·지속 동기화·RTC 최종 검증.
- 역방향 프록시 설치·기존80번 충돌 확인·로그인 검증.

## 대화에서 보완한 설명

1. TTL 24시간은 '내일부터 활성화'가 아니다. 기존 캐시와 음성 캐시가 별도로 영향을 준다.
2. `localhost`는 BIND 내장 ACL이다. loopback 한 주소만 허용한다는 표현은 엄밀하지 않다.
3. `ra`는 특정 클라이언트의 재귀 성공 증거가 아니다.
4. nslookup의 첫 PTR 실패와 `.lan` 접미사 조회를 실제 A 조회 실패와 구분한다.
5. `named.run` 순환 설정만으로 messages의 차단 로그가 줄지 않는다.
6. `rndc reconfig`는 설정 재적용에 쓰고, 기존 zone 파일 내용 변경은 zone reload 후 검증한다.
7. 로그의 부류가 달라졌다고 ACL 때문에 공격 종류가 바뀌었다고 단정하지 않는다.
8. 회선에서 보이는 주소·도메인이 이미 알려져 있어도 운영 대장에 필요한 세부 정보는 공유용 Git 문서와 분리한다.

## 후속 확인 목록

- [ ] 외부 권한 질의 A·SOA·TCP/UDP 양쪽 확인
- [ ] 비허용 클라이언트의 재귀·캐시 차단 확인
- [ ] 필요한 내부 사용자 재귀 정상 확인
- [ ] 로그 category·순환·디스크 증가량 확인
- [ ] parent/child NS 정합성 및 각 DNS 정상 확인
- [ ] 시간 동기화·RTC 최종 확인
- [ ] 웹서비스와 포트 생략 요청 별도 완료 확인
